Plataforma de agentes 24/7

Un asistente de IA personal que funciona sin parar, rodeado de un equipo de IA que lo diseña, lo despliega y lo repara cada noche.

TecnologíasOpenClaw, KVM, Docker, Python, Bash, systemd, SQLite, Ollama

El proyecto

Un asistente basado en OpenClaw funciona en una máquina virtual, responde en Discord y Telegram y ejecuta tareas programadas: seguimiento de nuevos modelos de IA, informes, copias de seguridad, base de conocimiento.

A su alrededor, un equipo de IA: Claude Cowork redacta las necesidades, Claude Code escribe el código y los procedimientos, y una tarea programada de Claude repara la plataforma cada noche. Solo me entero si la reparación ha fallado.

Lo que hice con IA

  • Una cadena de tres eslabones

    Cowork escribe el qué, Claude Code lee el código real y redacta una especificación técnica antes de programar, la VM lo ejecuta. Los archivos markdown son el contrato entre las IA.

  • Cada modelo en su sitio

    GPT para el diálogo y el criterio, MiniMax para el volumen, Ollama en la GPU local para las auditorías, Claude para el desarrollo y la revisión. Sin respaldo silencioso: un fallo de modelo se ve.

  • Ningún LLM en la fontanería

    Instalación, tests y vueltas atrás son 100 % mecánicos. Un script comprueba si hay trabajo antes de despertar a un modelo, y otro script valida lo que devuelve el modelo.

  • Una reparación nocturna acotada

    Recogida silenciosa a las 4:08, tarea de Claude a las 4:15, remedios limitados a una lista blanca, un solo intento por control, y un fallo solo cuenta si dos lecturas separadas por 60 s lo confirman.

  • Un healthcheck que nunca duerme

    32 controles ejecutados por 6 workers en paralelo en 7,5 segundos. Correo solo si hay un fallo, Telegram solo si es crítico, sin duplicados durante 6 horas y enviado directamente por la API para seguir localizable aunque la pasarela esté caída.

  • Una memoria que resiste a la compactación

    Un registro de sesión de 44 secciones fechadas, con las decisiones tomadas y el estado actual, y 17 archivos de memoria con el formato «por qué, cómo aplicarlo».

Lo que fue difícil

Una auditoría equivocada

El problema
Una primera auditoría atribuía los trabajos programados averiados a una causa equivocada y proponía 13 correcciones.
Lo que hice
Una segunda auditoría rastreó 9 trabajos, probó 6 hipótesis y declaró falsa la primera causa raíz.
El resultado
La causa real era una regresión que dejaba al agente sin ninguna llamada a herramientas que funcionara. Se corrigió una vez, en su origen.

Un job de LLM destructivo sustituido por un script

El problema
Un agente encargado de la copia de seguridad git improvisó un comando destructivo: cambios sobrescritos, copia duplicada, disco lleno.
Lo que hice
Análisis de la causa raíz y sustitución del agente por un script 100 % determinista: rutas limitadas, detección de secretos, ningún comando destructivo.
El resultado
La copia de seguridad ya no llama a ningún modelo. Ya no puede improvisar.

Un bot que se desconectaba

El problema
Dos tareas despertaban a un modelo cada 15 minutos en una VM de 2 núcleos. El bot de Discord perdía la conexión.
Lo que hice
Cambio al principio «comprobar antes de despertar»: un script mira primero si hay trabajo.
El resultado
Desconexiones de 28 por hora a 0, carga de 4,66 a 0,88.

Detener un proyecto por las cifras

El problema
Un pipeline de búsqueda de vulnerabilidades en smart contracts llevaba 4 meses funcionando: 53 155 candidatos, 1133 pruebas de concepto, 0 fallos explotables.
Lo que hice
Decisión de parar, archivo verificado, código versionado, controles de vigilancia retirados.
El resultado
Parada limpia, 0 fallos en 32 controles tras el desmantelamiento.

Seis falsas alarmas seguidas

El problema
El control de trabajos programados envió un correo de fallo seis noches seguidas: contaba un trabajo omitido como uno fallido.
Lo que hice
La regla se corrigió en el propio control, no se silenció en el correo.
El resultado
Las noches siguientes fueron silenciosas, porque no había nada averiado.
