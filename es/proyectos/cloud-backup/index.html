El proyecto

La aplicación controla rclone para copiar carpetas en la nube. Primero simula, muestra un balance con cifras, pide validación, y después ejecuta y verifica de forma independiente.

Cuando el cliente oficial de la nube destruyó miles de archivos, la investigación reconstruyó su funcionamiento interno hasta explicar la destrucción, consulta SQL a consulta SQL.

Lo que hice con IA

  • Un traspaso que fija las reglas

    El prompt de traspaso a Claude Code fija tres reglas: verificar en lugar de suponer, probar con un rclone real y no con mocks, no saltarse nunca las protecciones. Y: «dime cuando no estés seguro».

  • Un método forense con herramientas

    Lectura del código fuente de rclone para refutar una hipótesis, datación con el diario de NTFS, pruebas controladas de una sola variable, un test estadístico de secuencias, lectura del SQL en claro desde un build de depuración.

  • Dos agentes en paralelo

    Claude Cowork indexó y cruzó los datos, Claude Code analizó la base de datos. Los expedientes de la investigación se escriben para recargarlos tras cada compactación.

  • Las hipótesis refutadas se conservan

    Una tabla específica conserva las 11 hipótesis refutadas y los errores que la propia IA corrigió.

  • Una prueba de completitud tras cada transferencia

    Ambos lados se vuelven a listar tras cada transferencia. Cualquier archivo que falte marca la ejecución como incompleta y se convierte en un plan que solo puede añadir, nunca borrar.

  • Borrados limitados por el plan aprobado

    Cada transferencia recibe como tope estricto el número de borrados que aprobé. En el banco de pruebas, tres borrados locales adicionales se rechazaron y los archivos se conservaron.

  • Un banco de pruebas con la herramienta real

    El banco ejecuta el rclone real contra un remoto local, con 3000 archivos generados y 11 controles, para probar cada regla sin tocar la nube.

Lo que fue difícil

Una regla que lo habría destruido todo

El problema
5095 fotos destruidas por el cliente oficial. Borrar los archivos temporales parecía la solución.
Lo que hice
Lectura del funcionamiento interno: cada archivo temporal estaba indexado con el identificador en la nube de su destino.
El resultado
La regla habría destruido 12 801 archivos, en local y en la nube. Se corrigió antes de tocar nada.

Un éxito con 5386 archivos que faltaban

El problema
Una sincronización dada por correcta dejaba archivos fuera, y ocho reproducciones locales salían limpias.
Lo que hice
La defensa se entregó de todos modos: una comprobación de completitud tras cada transferencia.
El resultado
205 000 archivos verificados en 45 segundos, y un control de desviaciones programado.
