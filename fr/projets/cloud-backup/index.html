Sauvegarde cloud prouvée

Une sauvegarde qui prouve ce qu'elle a sauvegardé, puis l'enquête forensique, menée avec deux agents, qui a expliqué pourquoi le client officiel détruisait des fichiers.

Le projet

L'application pilote rclone pour sauvegarder des dossiers vers le cloud. Elle simule d'abord, présente un bilan chiffré, demande validation, puis exécute et vérifie de façon indépendante.

Quand le client officiel du cloud a détruit des milliers de fichiers, l'enquête a reconstitué son fonctionnement interne jusqu'à expliquer la destruction, requête SQL par requête SQL.

Ce que j'ai fait avec l'IA

  • Une passation qui fixe les règles

    Le prompt de passation à Claude Code pose trois règles : vérifier plutôt que supposer, tester avec un vrai rclone et pas des mocks, ne jamais contourner les protections. Et : « dis-moi quand tu n'es pas sûr ».

  • Une méthode forensique outillée

    Lecture du code source de rclone pour réfuter une hypothèse, datation par le journal NTFS, tests contrôlés à une seule variable, test statistique des séquences, lecture du SQL en clair d'un build de debug.

  • Deux agents en parallèle

    Claude Cowork a indexé et croisé les données, Claude Code a analysé la base. Les dossiers d'enquête sont écrits pour être rechargés après chaque compactage.

  • Les hypothèses réfutées sont gardées

    Un tableau dédié conserve les 11 hypothèses réfutées, et les erreurs de l'IA corrigées par elle-même.

  • Une preuve de complétude après chaque transfert

    Les deux côtés sont relistés après chaque transfert. Tout fichier manquant marque l'exécution comme incomplète et devient un plan qui ne peut qu'ajouter, jamais supprimer.

  • Des suppressions plafonnées par le plan validé

    Chaque transfert reçoit comme plafond strict le nombre de suppressions que j'ai validé. Sur le banc de test, trois suppressions locales de plus ont été refusées et les fichiers conservés.

  • Un banc de test avec le vrai outil

    Le banc fait tourner le vrai rclone contre un distant local, avec 3 000 fichiers générés et 11 contrôles, pour tester chaque règle sans toucher au cloud.

Ce qui a été difficile

Une règle qui aurait tout détruit

Le problème
5 095 photos détruites par le client officiel. Supprimer les fichiers temporaires semblait être la solution.
Ce que j'ai fait
Lecture du fonctionnement interne : chaque fichier temporaire était indexé avec l'identifiant cloud de sa cible.
Le résultat
La règle aurait détruit 12 801 fichiers, en local et dans le cloud. Elle a été corrigée avant tout geste.

Un succès avec 5 386 fichiers manquants

Le problème
Une synchronisation annoncée réussie laissait des fichiers de côté, et huit reproductions locales étaient propres.
Ce que j'ai fait
La défense a été livrée quand même : une vérification de complétude après chaque transfert.
Le résultat
205 000 fichiers vérifiés en 45 secondes, et un contrôle de dérive planifié.
