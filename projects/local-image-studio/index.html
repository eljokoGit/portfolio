The project

I started running AI locally: ComfyUI for image generation graphs, WorkflowUI to publish those graphs as simple apps, and a local LLM for text. To use them every day, I designed my own interface, a conversation where each message becomes an image.

It is a small FastAPI service with an Alpine.js page. The browser only talks to the service. The service calls a fixed list of WorkflowUI routes and reads ComfyUI without ever writing to it.

The screenshots come from a copy with demo conversations. The rewritten prompts they show are illustrative: that display is built and tested, and goes live with the next workflow version.

What I did with AI

  • Record the real server before coding

    Claude first explored WorkflowUI read-only, its API description and its front-end code, to find the exact request format. It then recorded a full real run, plus cancel, error and unknown-run cases. Only then did it write code.

  • Hidden behaviours, measured

    Without its field bindings, WorkflowUI answers 200 but runs the default values. A graph can report success with no image. A failed rewrite silently returns the typed prompt. Each trap was measured, written down and turned into a rule.

  • A local LLM in the pipeline

    Each idea is rewritten by a local LLM before diffusion. A copy of the workflow exposes the rewritten text, and a 4-line patch to the rewrite node makes Retry really run the rewrite again.

  • An allow-list, not a proxy

    WorkflowUI's admin routes are open on the local network, so the service must never relay arbitrary calls. It knows 12 WorkflowUI calls and 2 read-only ComfyUI calls, and caps every value: one image per run, sizes up to 2048 pixels.

  • Tests without a GPU

    58 tests run in under a second. They replay 24 responses recorded on the real server, errors included, with no hand-written fake.

  • Honest progress, no ghost messages

    Progress is streamed live and estimated from the last 100 runs; it stops at 95 % until the real end. Each message is saved before the run starts and removed if the server refuses it.

What was hard

A 200 that ran the wrong thing

The problem
On the first test run, WorkflowUI answered 200 but generated its default values: the request lacked the field bindings, and nothing said so.
What I did
Claude read the front-end code to find the exact body, then every call was recorded on the real server and replayed in the tests.
The result
The service always sends the bindings, and a test breaks if they disappear.

A success with no image

The problem
ComfyUI can report a run as successful while the image branch was rejected: one valid output node is enough for it.
What I did
A rule in the service: a finished run with no image is an error, shown in the conversation.
The result
An invalid setting now shows up as a clear error in 1.5 seconds, instead of an empty success.
