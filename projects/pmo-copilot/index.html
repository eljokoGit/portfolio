Multi-agent PMO copilot

Claude agents turn an IT programme's meetings and documents into a validated knowledge base, minutes, daily briefs and questions. The project manager stays the arbiter.

The project

I run an IT transformation programme at a large industrial group. After each meeting, an agent reads the transcript and writes structured minutes: decisions, actions with owner and due date, risks, open questions.

Every night, an orchestrator splits the work across specialised sub-agents, which fold these minutes and documents into a schema-checked knowledge base. When an agent is unsure, it asks instead of inventing. I answer from a web cockpit, and my answers are applied automatically.

This is the kind of system a company needs to make agents useful: a reliable knowledge base, clear roles, measured costs and a human who decides. The screenshots use a fictitious programme: no real data is shown.

What I did with AI

  • An orchestrator and 9 sub-agents

    The night orchestrator launches 7 modules in parallel, then 2 in sequence. They communicate through manifest files stored in one folder per run, which makes every night replayable and auditable.

  • The right model for each task

    Opus for semantic judgement (is this a decision or a fact?), Sonnet for constrained pipelines, Haiku for dispatchers and synthesis. The rule became non-negotiable after an incident.

  • Check before waking

    A Haiku dispatcher checks for work and only launches an Opus sub-agent when there is some. The orchestrator stops at step 0 if nothing changed. The quota is split into windows, and backups moved to a script with no AI.

  • A knowledge base that is the source of truth

    11 object types, 27 JSON Schemas, a validator run after every write with rollback on violation, atomic writes, and a detector for sources that silently stop feeding the system.

  • Minutes with guardrails

    A 657-line skill: a strict rule between decision and fact, misheard names sent for validation, an action with no owner or date treated as an intention, locked writes and loss-free reconstruction.

  • A human who decides, in writing

    The cockpit never writes to the base. Each answer creates a file that an agent interprets, then archives. An explicit confirmation always beats an inference.

  • A system that proposes its own improvements

    Every week, an agent proposes an improvement to the system. A written self-critique showed it piled up information without challenging it: that led to the redesign described below.

  • A cockpit built and tested with Claude Code

    20 pages, 68 API endpoints, 23 validation schemas and 401 automated tests, with architecture decision records. It reads the base and never writes to it.

  • Skills packaged as a plugin

    6 context skills, one per sub-domain, load the right context on demand. They ship in a plugin, alongside about fifteen domain skills.

The cockpit, where I decide

Every doubt raised by an agent lands in a queue, with its source, what happens if I confirm it, what happens if I reject it, and a suggested action. My answer becomes a file that an agent applies at night. The screens below use an invented programme.

Measure first, then model in UML

After six months in production, the weekly self-critique raised a doubt: the base was growing, but was it getting better? Before touching anything, I had the agent measure it. The verdict: the system filled up much faster than it emptied. Only 4 % of questions had ever been closed, 5 % of decisions superseded, and no fact had ever expired.

We then worked in UML, with Mermaid, so that every diagram stays editable and versioned. The class diagram showed in one picture what the text could not: the dotted links, the ones that close a question or re-examine a decision, did not exist. Out of 1,636 objects, there were exactly three links between objects.

The state diagrams made the broken lifecycles visible. A fact had no terminal state, so the base could only grow. A decision went straight from in force to superseded, so none was ever re-examined when the fact behind it fell. Two new states fix this: superseded for a fact, to re-examine for a decision.

Who does what, when, on what basis

With several agents, the real risk is a tangled machine where nobody knows who decides. So I asked for a sequence diagram per scenario, with every actor, and I challenged each arrow. When the agent wrote that the orchestrator saw everything, I asked what exactly it loads into its context. It had never been defined: the agent measured it, then we wrote it down.

  • A task is defined by what it is given

    Each step lists its material, its context and its tools. Roles are not decided upfront: they emerge where the context stays stable.

  • The orchestrator never reads the whole base

    It reads the agents' reports and the day's delta: 9 changed objects on an ordinary day, 132 in a week. The topic map weighs 16 KB. A small context, by design.

  • Agents do not call each other

    An agent works and reports. Only the orchestrator sends orders, grouped by expert: two runs instead of seven on the measured scenario.

  • A free task is never free

    A cheap keyword matcher was dropped: it linked 8 % of objects on a word found in a justification. Noise has a cost, because someone has to remove it.

Build first, clean up after

The system is in production and the cockpit reads the base all the time, so the plan follows one constraint: nothing may break. The agent checked the code before ordering the steps. Adding a field breaks nothing, because the schemas tolerate unknown fields. Deleting an object type does: one of them is read by 11 backend files and a dedicated page.

Hence the order: first the additive steps, then the cleanup. And one discovery unlocked everything: the field used to attach objects to topics was read by no file of the cockpit, so it could be replaced by the new link with zero impact.

Operations in numbers

Everything the agents do leaves a trace: a manifest per sub-agent run, a result file per scheduled task, a file per doubt. These charts only count those traces. The most telling one is the last: most of the agents' doubts were rejected by me, which is exactly why they ask instead of acting.

What was hard

The sub-agent that claimed a folder did not exist

The problem
Run on a model that was too light, a module wrote "folder missing" while 87 files were there. Three meetings vanished from the brief.
What I did
Models enforced per module, the initial check run directly, cross-checking by script, automatic retry on a false absence, and a loud stop if the path is empty.
The result
A completeness check now recomputes every module's condition.

The invented approvals

The problem
A fallback matched unaddressed feedback to proposals in chronological order. Five proposals were wrongly "confirmed", one of them implemented.
What I did
Inferring intent is banned: only an explicit verdict field counts.
The result
The wrong implementation was reverted the same day, and the rule now applies system-wide.

Never forgetting means piling everything up

The problem
The "never deduplicate" rule had produced 253 open actions, 110 of them already resolved and 72 duplicates.
What I did
Rule reversed: attach to what exists, close only with evidence, and raise a doubt when the resolution is only inferred.
The result
An action list a human can work with again.

A single writer

The problem
Doubts written by several agents on several machines caused 4 duplication and corruption incidents.
What I did
Only one process may now write, with deduplication, a monotonic ID, a lock and atomic writes.
The result
Load test: 50 parallel calls in 5 variants produce exactly 5 IDs.
